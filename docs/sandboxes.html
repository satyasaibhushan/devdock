Sandboxes Vercel-style previews for a ticket that spans several repos. The ticket's changed services run its code; every other service falls through to UAT.

TL;DR
A sandbox is a ticket key bound to a namespace slot plus a list of members (repo + workload + PR or branch). Members are built as persistent images from detached git worktrees and helm-upgraded over the slot's UAT proxy releases. Short in-cluster service names resolve inside the slot, so members call each other and everything else proxies to uat-us. Pods sleep at 0 replicas until woken. Unused for 24h, a sandbox expires: its slot is reset and freed, the record stays for a one-click rebuild. Nothing is deleted except by an explicit agent or human call.

1 · Why

One ticket often lands as PRs in 3 to 4 repos. Reviewing it today means merging into -uat branches or hand-running dev pods. Dev namespaces already proxy every API to UAT through ExternalName services (dev-env env:create in vmockinc/devops), and devspace deploy swaps a proxy for real code on the same release name. Sandboxes automate exactly that, per ticket.

Cluster sleep facts that shape the design: the devspace-sleep CronJobs only scale deployments labelled devspace.sh/replaced=true (dev mode). Persistent deploys never carry that label, so sandboxes are untouched by them. The UAT nodegroup ASG goes to 0 from 01:00 to 09:00 IST; awake sandbox pods simply reschedule when nodes return.

3 · Model

interface Sandbox {
  key: string                 // ticket key as typed: 'SULF-1234'
  title?: string
  slot?: string               // namespace currently leased; unset while expired
  state: 'creating' | 'active' | 'expired' | 'failed'
  createdAt, lastUsedAt: number
  members: SandboxMember[]
  activity: ActivityEntry[]   // newest last, capped at 200
  snapshot?: SandboxSnapshot  // what the last complete build deployed
  expiredAt?: number
  error?: string              // last failed operation
}
interface SandboxMember {
  repo: string                // devdock repo id
  workload: string            // 'api' | 'ui' | 'worker' | 'cron' …
  source: { kind: 'pr', repoSlug, number, url } | { kind: 'branch', ref } | { kind: 'worktree', path }
  mode: 'built' | 'dev'
  headSha?, deployedSha?: string
  dirtyFiles?: string[]       // worktree paths baked beyond deployedSha
  image?: string              // content-addressed ECR ref of the last build
  build: { state: 'idle'|'queued'|'building'|'failed', instanceId?, startedAt?, error? }
  merged?: boolean
}
interface SandboxSnapshot {
  at: number, actor: string
  members: { repo, workload, sha, dirtyFiles: string[], image: string }[]
}
interface ActivityEntry { at: number, actor: string, action: string, detail?: string }
  • Power (awake | asleep | partial; unknown when cluster reads fail) is derived from the cluster on each reconcile, never stored.
  • actor is required on every mutation: you, agent:<name>, poller, sleeper, expiry.
  • Personal sandbox: the kube context namespace (saibhushan) is shown as a sandbox whose members are today's repos in dev mode. It is a view over existing repo state, not a record, and keeps today's runtime behaviour exactly.
  • Workers and crons default to 0 replicas: they would consume UAT's SQS messages. A member must name them explicitly.
  • Snapshot: a record, not storage. Images are already content-addressed in ECR; the snapshot names which image each member showed, at which sha, plus any uncommitted paths. It is written after every build that leaves all members deployed, and on demand.
  • The view adds link (the stable per-ticket URL, §10), markdown (a PR-body block: state, link, live URL, per-member repo workload sha (+N uncommitted files) against the source head), healthy, ribbon, pool and evictionCandidate.

4 · Namespace slots

  • The pool is DEVDOCK_SANDBOX_NAMESPACES (comma list), e.g. saibhushan-sb1,saibhushan-sb2. Infra creates them once with dev-env env:create <slot> --owner_uid <email>.
  • A sandbox leases one free slot on create or rebuild. The lease is a ConfigMap devdock-sandbox in the slot holding {key, instanceId, members, shas}. A slot whose ConfigMap names another key is busy. An operation claim in the same ConfigMap serializes lifecycle mutations across instances using resourceVersion compare-and-swap. It is separate from controller leadership.
  • Pool size caps concurrent sandboxes, ECR tags (IMAGE_TAG is <slot>-<workload>, overwritten per build) and cost.
  • The personal namespace may be listed as a slot for trials. A member whose release is held by a live dev session there is refused, never clobbered.
  • URLs are read from the slot's Ingress objects (authoritative), e.g. dashboard-<slot>.vmock.dev, api-<slot>-<team>.vmock.dev/<svc>. The UI shows ticket → URL, so slot names never matter to the reader.

5 · Building a member

  1. Worktree: detached checkout at headSha beside the parent checkout (same placement rule as replicas: outside any sync root), path ../.devdock-sb-<slot>-<member-hash> (a stable hash of repo + workload, so two workloads of one repo can use different heads). PR heads are fetched as pull/<n>/head from the PR's repo, so fork PRs work.
  2. A worktree source bakes an agent's checkout as it is: git ls-files -co --exclude-standard (tracked and untracked, ignored and deleted excluded) is copied into a devdock-owned temp build dir next to the member path and built from there, so generated configs never land in the agent's checkout. headSha is that checkout's HEAD; dirtyFiles are the changed and untracked paths. The controller does not poll worktree members; devdock_sandbox_snapshot rebuilds them from current files.
  3. Env: devspace run-pipeline sync-env in the worktree with --var ENVIRONMENT_NAME=<slot>, so prepare_local_env rewrites hosts for the slot.
  4. Deploy: devspace deploy -n <slot> -p persistent with vars ENVIRONMENT_NAME=<slot>, WORKLOAD_TYPE=<workload>, API_PERSISTENT_REPLICAS/WEB_PERSISTENT_REPLICAS = current power (0 asleep, 1 awake), CRON_/WORKER_PERSISTENT_REPLICAS=0 unless named.
  5. Placement: the persistent profile pins nodeSelector: workload: products (the UAT nodegroup). A generated, untracked config in the worktree adds a values file setting workload: development so sandboxes never consume UAT capacity.
  6. Same tag every build, so an awake member gets a rollout restart after a successful deploy.
  7. One build per (sandbox, member). A newer headSha marks the running build stale; it restarts from the new head when done (latest wins).

6 · Wake and sleep

  • Wake: if any member is stale (deployedSha ≠ headSha) build it first, then patch spec.replicas=1 on each member's api/ui deployment. Typical 20 to 60s when nothing is stale.
  • Restore: wake on an expired sandbox with a retained snapshot leases a free slot and deploys the recorded images with --skip-build; nothing is rebuilt. A full pool fails naming the least-recently-used asleep sandbox; evict: true expires that one first. Awake, building or creating sandboxes are never evicted. Without a snapshot the call fails: rebuild first.
  • Sleep: patch spec.replicas=0. Images and releases stay.
  • Both are any-machine operations: only builds and dev sessions are tied to a machine.

7 · Lifecycle and expiry

creating ──▶ active ──(unused DEVDOCK_SANDBOX_TTL_HOURS, default 24)──▶ expired
                 ▲                                                     │
                 ├──────────────── rebuild (new slot lease) ◀──────────┤
                 └── restore (recorded images, skip-build) ◀───────────┘
                     while the snapshot is retained (DEVDOCK_SNAPSHOT_TTL_DAYS, default 30)
   any state ──(explicit delete by agent or you)──▶ gone
  • Used = wake, build, or any mutating MCP/UI call. Request traffic is not tracked.
  • Expire: reset every member release in the slot to its default (UAT proxy for api, purge for others; a generated reset pipeline runs create_deployments default for api and purge_deployments for other members; the shared UI purge pipeline restores a proxy, so it cannot implement the non-api rule directly), delete the slot ConfigMap, remove worktrees, free the slot. Keep key, members, last shas, activity.
  • Rebuild: lease a slot, build every member at current head, leave asleep unless asked to wake.
  • Merged PRs: member gets merged: true and stops building. Never auto-deletes. When all members are merged, status says so for an agent to act on.
  • Delete: explicit only. Expires first if active, then removes the record.

8 · State and recovery

  • stateStore gains sandboxes: Record<key, Sandbox> (same atomic JSON file).
  • The slot ConfigMap mirrors key, members and deployed shas, so a lost state file is rebuilt from the cluster on boot, matching devdock's rule that the cluster is the source of truth.
  • Long work (create, build, rebuild, expire) runs as durable Operations; interrupted ones are marked interrupted, never replayed.

10 · HTTP

GET /sandboxes, GET /sandboxes/:key, POST /sandboxes, PATCH /sandboxes/:key, POST /sandboxes/:key/{build,snapshot,wake,sleep}, DELETE /sandboxes/:key. Read-only discovery is GET /sandboxes/:key/discover; controller parity adds POST /sandboxes/:key/{expire,head}. Every mutating body requires actor. Sandbox changes are pushed over the existing websocket as sandbox events.

Stable link: GET /s/:key on the daemon (http://127.0.0.1:7717/s/SULF-1234) is the one URL a ticket or PR carries. Awake and healthy: 302 to the live URL. Asleep: the daemon triggers a wake (actor link) and serves a self-contained snapshot card that polls GET /sandboxes/:key and redirects when ready. Expired with a retained snapshot: the card offers Restore, or Evict and restore when the pool is full. No snapshot: a 404-style card. A failed wake shows its error; outside node hours (§2) that error is what the reader sees.

11 · Controller

  • Leadership: ConfigMap devdock-controller in the personal namespace, {holder, renewedAt}, renewed every 30s via resourceVersion CAS; another instance takes over after 90s of silence. Default holder: vmockbox (inside the network, no VPN). The Mac takes over when it is down.
  • Poller (60s): for each active sandbox, read PR head sha and merged state with gh; record new heads with actor poller.
  • Debounced builds: build a stale member after 5 min of quiet while asleep, 30s while awake.
  • Idle sleep: awake sandbox with no use for 30 min goes to sleep (actor sleeper).
  • Expiry: hourly sweep per §7 (actor expiry).
  • Builds may run on any instance that has the repo checked out, Docker and ECR auth; the leader assigns, a caller may pin an instance.

Controller implementation deviations: every action records actor controller. Leadership has no preferred host; any instance in DEVDOCK_CONTROLLER=auto (default) may acquire it, while off disables acquisition. Builds run locally on the leader through the existing lifecycle, without assignment or instance pinning. Branch heads are polled alongside PR heads. Scheduling runs on the 30s renewal tick, so a quiet period may finish up to 30s before a build starts. Failed heads require an explicit retry or a new head; controller head observations preserve idle and expiry clocks.

13 · Replicas

Unchanged in this round. A one-repo sandbox supersedes a replica (own hostname, callers reach it). Replicas are removed after a live proof confirms sandboxes work end to end.

14 · Infra asks

  1. Create 2 to 3 slots: dev-env env:create saibhushan-sb<n> --owner_uid <email>.
  2. A PriorityClass below the autoscaler's expendable cutoff (value < -10) so sandbox pods only use spare capacity and never add a node.
