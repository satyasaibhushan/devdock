devdock A global control plane for DevSpace sessions — start, kill, build, and attach to dev pods across every repo, from one daemon. Built for a human at a menu bar and an AI agent over MCP, sharing the same brain.

TL;DR
A headless daemon (always-on, launchd) wraps the devspace and kubectl CLIs. It launches each devspace dev inside its own tmux session, streams logs and PTYs over websockets, and reconciles live state from the cluster. On top sit thin clients that all call the same core service layer: a menu-bar GUI + web view for you, and an MCP server for the agent. Stack is TypeScript end-to-end, with node-pty ↔ xterm.js for terminals and Tauri for the tray.

1 · What it is

Today, working with DevSpace means walking each repo by hand: cd in, run devspace dev, leave a terminal hostage to its foreground sync, repeat for every service, and remember to devspace purge when you're done (you don't). devdock makes that a single pane of control.

devdock is a local service that knows about every repo on your machine with a DevSpace config, and lets you — or an agent — start, kill, build, watch, and shell into any of them without touching a terminal or remembering a namespace. It is not a Kubernetes IDE and not a DevSpace replacement; it is a thin, opinionated orchestrator over the tools you already trust, exposing them through one consistent surface.

2 · The dual mandate

devdock exists to serve two users with the same nouns but different verbs, and that duality is the central design force.

The human (you)

Wants glance + click. "Which devspaces are up right now? Kill career-service. Show me why the pod crashed." A menu-bar dot cluster and two-click controls.

The agent (Claude)

Wants call + read. devdock_status(), devdock_logs(), devdock_exec("python main.py"). It restarts a crashed pod and re-reads logs without a human in the loop.

The unifying insight
Both clients hit the identical core service layer. The read-only vs read-write terminal distinction you want for yourself is the permission scope for the agent: a read-only MCP token can observe and diagnose but not touch the pod; a read-write token can restart and run. One lock, two clients. Build the brain once.

4 · The three layers

devdock is three thin layers over devspace + kubectl + tmux. Nothing below is novel infrastructure; the value is the combination in one always-on service.

  ┌─ CLIENTS ────────────────────────────────────────────────────────┐
  │   menu-bar GUI + web view          MCP server          CLI         │
  │   (you: glance + click)         (agent: call+read)   (scripts)      │
  └───────────────┬───────────────────────┬───────────────┬──────────┘
                  │  same HTTP/WS API     │  same functions │
  ┌─ CONTROL DAEMON  (the only brain, headless, launchd) ─────────────┐
  │                                                                    │
  │   registry     scan ~/Code/**/.devspace/*/devspace.yaml         │
  │   reconciler   desired state  ⇄  actual cluster state           │
  │   supervisor   spawn/track devspace dev|deploy|purge            │
  │   ptyBroker    node-pty ⇄ websocket, ro/rw lock                 │
  │   logTailer    kubectl logs -f → ring buffer → ws subscribers   │
  │   crashWatch   pod restartCount + traceback scan                │
  │   stateStore   SQLite: repos, sessions, last-known status       │
  │                                                                    │
  └───────────────┬────────────────────────────────────────────────────┘
                  │  subprocess + websocket
  ┌─ EXECUTION  (tools you already run) ──────────────────────────────┐
  │   devspace dev   → inside  tmux new-session -d -s devdock-<repo>    │
  │   kubectl logs/exec/attach → against any pod in the cluster         │
  │   tmux attach (-r)         → read-write / read-only terminal        │
  └────────────────────────────────────────────────────────────────────┘
The architectural rule
The core service layer has zero transport knowledge. Fastify routes, the websocket handlers, and the MCP server are all thin callers of core. This is what keeps the human GUI and the agent's MCP verbs from ever drifting — they are two doors into one room.

5 · The tmux decision (the one that makes it easy)

devspace dev is a long-running foreground process: it holds the file sync, the port-forward, and the in-pod terminal. If the daemon spawns it as a plain child and the daemon restarts, dev mode dies with it. The fix that unlocks everything: launch each devspace dev inside its own named tmux session.

# start
tmux new-session -d -s devdock-career-service-agents \
    'cd ~/Code/backend/career-service-agents && devspace dev'

# the daemon never blocks on it; tmux owns the process

That single decision hands you, for free:

BenefitHow
Survives daemon restartstmux outlives the daemon; on boot the daemon re-discovers sessions by name
Read-only terminaltmux attach -r -t devdock-<repo> — exactly your "listen" mode
Read-write terminaltmux attach -t devdock-<repo> — type python main.py
Web terminalnode-pty spawns the tmux attach command; pipes to xterm.js over ws. No ttyd needed.
Multiplexingtmux is single-pane; many viewers, one writer — gate the rw attach behind a lock
Consequence
The "two permission levels" — listen vs control — are not something you build. They are tmux attach -r vs tmux attach. The daemon just chooses which command node-pty spawns based on the requester's grant.

6 · Reconciliation: state comes from the cluster

devdock never trusts its own memory of "what's running." It reconciles: on boot and on a timer, it queries the cluster for reality and merges it with its registry. This makes it crash-proof and lets it adopt pods it never started.

// reconcile loop (every few seconds + on demand)
for repo in registry:
    pods   = kubectl get pods -n <ns> -l svc=<workload> -o json   // your selector
    session = tmux has-session -t devdock-<repo>
    status  = derive(pods, session):
        - tmux session + ready pod        → RUNNING (managed)
        - ready pod, no tmux session      → RUNNING (external)
        - pod with restartCount>0 / crash → CRASHED
        - no pod, no session              → STOPPED
StateMeaningWhat you can do
RUNNING (managed)devdock launched it via tmux + devspace devfull lifecycle: kill, attach, logs, restart
RUNNING (external)someone else / a prior session / a plain deploylogs, exec, attach, kubectl restart — but doesn't own the sync
CRASHEDpod up but entrypoint died / restart-loopingread logs, re-run main.py, restart
STOPPEDnothing in cluster, no sessionstart, build

7 · The verbs in full detail

Start

tmux new-session -d -s devdock-<repo> 'cd <path> && devspace dev'
# daemon then: tail the tmux pane for build progress, watch pod readiness,
# flip status STOPPED → BUILDING → RUNNING(managed) as the pod goes Ready

Build

cd <path> && devspace deploy
# builds run IN-CLUSTER (BuildKit, per the repo's devspace.yaml) →
# the heavy compile does NOT tax the laptop CPU

Kill

cd <path> && devspace purge   &&   tmux kill-session -t devdock-<repo>
# frees cluster resources AND stops the local file-sync watcher

8 · Terminal access (read-only & read-write)

The terminal panes are the technically richest feature, and the reason the whole stack leans TypeScript. The canonical pairing is node-pty (spawns a PTY) ↔ xterm.js (renders it in the browser), bridged over a websocket.

// daemon: open a terminal for a client
function openTerminal(repo, mode):           // mode = 'ro' | 'rw'
    if mode == 'rw': acquireWriteLock(repo)    // one writer at a time
    cmd = mode == 'ro'
        ? ['tmux','attach','-r','-t',`devdock-${repo}`]
        : ['tmux','attach',     '-t',`devdock-${repo}`]
    pty = nodePty.spawn(cmd[0], cmd.slice(1), {cols,rows})
    pty.onData(d => ws.send(d))                 // pod → browser
    ws.onMessage(d => mode=='rw' && pty.write(d)) // browser → pod
ModeCommand node-pty spawnsGrant required
Listen (read-only)tmux attach -r or kubectl logs -fany client / read-only MCP token
Control (read-write)tmux attach or kubectl exec -it … bashwrite-lock holder / read-write MCP token
Attach to entrypointkubectl attach -it <pod>connects to PID 1 — watch the live crash

9 · Interacting with existing pods

Pod interaction is pure kubectl against the cluster — independent of whether devdock launched the pod. Reconciliation (§6) surfaces external pods; then all three interaction modes work on any running pod:

ModeCommandUse
Listenkubectl logs -f <pod> -c <container>live stdout incl. tracebacks, zero risk
Shellkubectl exec -it <pod> -- /bin/basha new shell — run main.py, inspect
Attachkubectl attach -it <pod>the actual entrypoint process's stdio

DevSpace also ships config-aware wrappers — devspace enter --pod <pod> and devspace attach — that pick the pod from the repo config, so you don't hand-write selectors. Raw kubectl is more universal; devspace enter is more ergonomic. devdock can offer both.

10 · Crash handling

The "python main.py dies and stays dead" problem. devdock detects it two ways and offers recovery:

  • Pod-level: watch kubectl get pod -w / restartCount — a climbing count means a restart loop.
  • Process-level: scan the tailed log stream for tracebacks / non-zero exit markers; the entrypoint can be supervised so a dead main.py doesn't take the pod with it.

Recovery: a health probe + one-click (or devdock_exec) re-run in the pod, and an optional supervised restart loop in the entrypoint so a crash self-heals. This is the exact capability the autonomous-dev nightly run needs to recover unattended.

WS    /repos/:id/terminal?mode=ro|rw   // node-pty ⇄ tmux attach
WS    /events                     // status changes, crash events (drives the tray dots)

14 · MCP face (the agent's hands)

A second entry point over the same core functions. Read-only vs read-write is a property of the agent's token.

devdock_list()                    → repos + status
devdock_status(repo)              → RUNNING|CRASHED|STOPPED|EXTERNAL
devdock_start(repo)               → devspace dev
devdock_build(repo)               → devspace deploy
devdock_stop(repo)                → devspace purge
devdock_logs(repo, tail=200)      → recent log lines  (read-only OK)
devdock_exec(repo, "python main.py")  → run in pod    (read-write only)
Why this matters
With these verbs the autonomous-dev loop can: detect a crashed pod (devdock_status), read the traceback (devdock_logs), fix the code, and restart (devdock_exec) — with no human in the loop. devdock is the actuator that vision was missing.

16 · Performance — will it slow the laptop?

The daemon itself: no. Idle subprocess manager + log tailers + websockets — a few tens of MB RAM, ~0% CPU at rest.

The cost is what it runs, and devdock is the cure, not the cause:

  • Builds run in-cluster (BuildKit per the repo's devspace.yaml) → the heavy compile is off your machine.
  • The real local cost is the file-sync watcher inside each running devspace dev — scales with (running repos) × (files watched). The killer is watching node_modules/.venv/.git.
  • Because kill = purge is one click, you run only the repos you're touching — net less load than the status quo of leaving everything up.

Mitigations baked in

  • Sync excludes for node_modules, .venv, .git, build dirs.
  • "Pause sync" on idle repos without a full purge.
  • Per-repo resource readout in the UI so you can spot the hog.

17 · Phasing

  1. Phase 1 — daemon + web UI. TS daemon (registry, reconcile, supervisor, ptyBroker, logTailer) + a browser dashboard with xterm.js. Start/kill/build/logs/terminal on localhost. This is the whole product minus polish.
  2. Phase 2 — Tauri menu-bar. Tray with glanceable status dots; click to pop the web UI for the one repo you care about. Now it's an always-there background app with a face.
  3. Phase 3 — MCP server. Trivial once core exists — a second entry point over the same functions. This is what plugs devdock into the autonomous-dev machine.

18 · The bigger machine devdock plugs into

devdock isn't a side project — it's the control plane for a larger goal: handing development of a backend module to an AI agent and getting out of the loop. That machine has a substrate (fast DB access, stable pod, token/latency signals), a verification spine (eval + score timeline), and a Jira intake/outflow ring. devdock is the piece that lets the agent operate the pod itself:

  • Restart a crashed main.py during a nightly run.
  • Read logs to diagnose a failing flow.
  • Wait on real pod readiness instead of a human watching a terminal.

Its read-only/read-write toggle becomes the dial for how much autonomy the agent gets. Same control surface, two operators.

19 · Design rules (non-negotiables)

  1. One brain. All logic in core; clients are thin. GUI and MCP never diverge.
  2. Don't reimplement the CLIs. Shell out to devspace/kubectl; never a k8s client lib for v1.
  3. State from the cluster, not memory. Always reconcile; adopt external pods; survive restarts.
  4. tmux owns the long-running process, never the daemon's own child handle.
  5. One writer per terminal. Read-only is the default; write is a held lock / scoped token.
  6. API-first. Daemon HTTP/WS is the contract; menu-bar, web, MCP, CLI are all clients of it.
  7. Light by default. Always-on means low idle footprint; Tauri over Electron; purge over leaving things up.
